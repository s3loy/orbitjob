# 取消运行

取消操作记录停止请求。只有获得充分的归属和终止证据后，Operator 才确认最终
结果。确认请求已被接受的 HTTP 响应，不能证明工作负载代码已经停止。

## 开始前

取消作业运行需要获取其实例数字 ID 和 `instance:Cancel` 权限。请求停止后，
使用 `instance:Get` 观察运行。实例路由要求凭据不受资源组限制。工作流使用
独立取消路由和 `workflow:Trigger` 权限；随后检查父工作流和步骤结果。

确认目标工作区、运行和 Attempt。取消不能撤销容器已经产生的外部副作用。

## 请求取消

在 Console 中打开运行并选择取消操作。检查当前阶段并确认请求。也可以执行：

```sh
RUN_ID=73
orbitjob runs get "$RUN_ID"
orbitjob runs cancel "$RUN_ID" --json
orbitjob runs get "$RUN_ID" --json
```

将 `73` 替换为实际运行 ID。响应报告请求时的资源引用和阶段。继续读取同一运行，
直到 Operator 报告已确认的终态结果。

## 解读结果

| 观测结果 | 必须采用的解释 |
|---|---|
| `CancelRequested` | 已记录停止意图；仍在检查终止。 |
| `Canceled` | 已确认请求的取消。 |
| `Succeeded` 或 `Failed` | 已确认的执行结果保持最终性；取消不会替换它。 |
| `CancelUnknown` | 平台尚不能证明已完成请求的停止。保留证据并继续恢复。 |
| `ExecutionUnknown` | 执行结果仍未验证；请求取消仍需要停止证明。 |

Operator 通过身份和版本检查缩短原始 Job 的截止时间，等待控制器确认停止，
并持久化完整的所属 Pod 终止证据。它在前台删除前释放证据 finalizer，并根据
保留的证明确认停止。Job 删除时间戳、空 Pod 列表或 UID 缺失均不能证明终止。
五分钟确认窗口使用已持久化的取消时间，并在重启后保留；达到窗口不会将不确定
状态转为 `Canceled`。

Workflow 取消会阻止新步骤，并请求取消非终态步骤。已经运行的同级步骤仍可观察。
工作流必须等待它们的确认结果；父运行停止不能证明所有容器都已停止。

## 恢复丢失的取消响应

先读取同一运行。保留其原始命名空间、名称、触发标识和运行 ID。如果当前状态确认
停止意图或最终结果，应继续依据该观测处理。如果没有可用结果，使用原始运行的
取消操作进行有意重试。原始运行仍可能执行时，不要创建替代运行。

对于 `CancelUnknown`，管理员必须检查原始 Job、保留的 Pod、台账和 Operator
错误。强制删除 Pod、移除证据 finalizer 或删除台账行，可能破坏恢复所需证据。
平台没有公开的强制裁定端点。请参阅
[执行恢复](../architecture.md#execution-recovery-and-concurrent-admission)。
